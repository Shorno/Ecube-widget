01

Four applications, four clear jobs.

The platform is easiest to understand when each repository is treated as one operational boundary rather than as a collection of pages and endpoints.

Ks-Tournalink-Backend

System of record

Owns tournament structure, match lifecycle, team and player state, scoring, analytics, vMix JSON, and live broadcast events.

Ks-Tournalink-Desktop-App

Telemetry ingress

Receives local PCOB traffic, feeds meaningful match changes to the Backend, and serves local map and player overlays to OBS.

Ks-Tournalink-Frontend

Operations console

Lets operators configure tournaments, activate matches, edit scores, inspect vMix data, and control broadcast presentation.

Ecube-widget

Presentation runtime

Fetches broadcast data, listens for live events, renders animated OBS graphics, and provides replay control and output pages.

What is the backbone?

The central business backbone is the Backend’s TournamentDataStore and TournamentDataEngine, backed by MongoDB. This is where the tournament aggregate becomes usable for scoring, analytics, vMix responses, and live broadcasts.

For real-time gameplay, the Desktop App is the ingress backbone because it is the only production component that directly receives high-frequency PCOB data.

How data moves.

There are three major runtime paths: configuration, live telemetry, and broadcast presentation. Replay currently sits outside the production path.

Operator Creates tournaments, assigns slots, and activates a match.
Admin Frontend Authenticated REST requests through Axios and Pinia.
Backend + MongoDB Persists structure and establishes the active match context.
PUBG / PCOB Posts player, kill, observer, circle, and global map payloads.
Desktop App :10086 Updates local overlays and filters the Backend statistics feed.
Engine processors Normalize state, compute deltas, persist scores, and broadcast events.
vMix REST + WebSocket Scoreboards, MVP, summaries, rankings, and live eliminations.
Ecube-widget Transforms data into themed, animated broadcast views.
OBS / Broadcast Captures the widget display iframe and local map overlays.
Local visual path Movement, circles, and global map information stay in Desktop memory and reach the local OBS map through SSE.
Backend statistics path Only meaningful statistical changes, kills, and observer changes are forwarded when the operator enables Feed Data.

Responsibility of each project.

These boundaries show where new features should live and which application should not be asked to own them.

REPOSITORY 01

Backend

NestJSMongoDBMongooseWebSocket

The authoritative tournament platform and business engine.

Owns

  • Users, authentication, tournaments, stages, groups, matches, teams, players, images, and sponsors.
  • Match activity, start/running/finished/completed lifecycle, and captured game ID.
  • Current normalized player and team state, manual scoring, and derived analytics.
  • Public /vmix/:tournamentId/... responses and /tournament live events.

Important processing sequence

  1. Load the tournament aggregate into TournamentDataStore.
  2. Validate incoming match and game identifiers.
  3. Compare previous and current PCOB state.
  4. Upsert current player/team documents and update the in-memory aggregate.
  5. Emit eliminations, achievements, ranking changes, and match-end events.
Does not own replay history today It overwrites the latest raw match snapshot and normalized scores. Historical positions, circle movement, and plane data are not persisted.

05

Why one replay becomes 100 MB.

The recording is a diagnostic event dump, not a purpose-built replay format. It records far more information than the replay UI consumes.

100
MB

The standalone tools/pcob-capture.js server appends every POST body, including unchanged events, to one JSONL stream. Each line repeats complete PCOB snapshots. New capture sessions can also be appended to the same file.

Current browser cost

  1. file.text() loads the complete file as a JavaScript string.
  2. The parser splits the entire string into lines.
  3. Every line is parsed before unchanged records are discarded.
  4. Remaining events still contain complete PCOB bodies.
  5. The normalized dataset is copied again through BroadcastChannel.

What replay actually needs

totalmessage

Player UID, team, name, rank, live state, position; team ID, name, alive count, kills, and logo URL.

setcircleinfo

Circle status/index, counter, maximum time, and displayed game time.

setgameglobalinfo

Circle geometry plus plane start and stop coordinates.

setkillinfo

Victim UID, causer name, and victim name for map markers and the kill feed.

setisingame

The current lobby or in-game phase used by the replay status display.

setobservingplayer

The observed player UID, stored in the payload’s "0" field.

The key conclusion Most raw combat, damage, healing, equipment, network, survival, and scoring fields in each full snapshot are unnecessary for map replay. They should be removed at the Desktop capture boundary rather than parsed and discarded in the browser.
06

Where the four projects have drifted.

These are current integration problems, not theoretical risks. They should be resolved before adding more cross-project features.

  1. Two widget control planes

    The Admin Frontend sends Backend WebSocket commands, while the actual Widget display listens to Widget SSE. The paths do not meet.

  2. Widget URL mismatch

    The Admin Frontend generates URLs without userId; current Widget routes require it and use different slugs.

  3. Duplicate catalogs

    Widget definitions exist in several Frontend and Widget files, and the copies have already diverged.

  4. Map port mismatch

    Desktop serves the map on 10086, while the Widget catalog points to 10087.

  5. Unowned PCOB port

    The Widget is configured for localhost:8080, but none of the four inspected repositories owns that service.

  6. No shared schemas

    Routes, event names, widget slugs, and DTO shapes are independently declared, making further contract drift likely.

07

A cleaner target architecture.

Preserve each application’s natural ownership and move replay optimization to the source of the high-frequency data.

STEP 01

Capture

Desktop receives the complete PCOB stream before its statistics filter.

STEP 02

Project

Desktop keeps only versioned replay fields, changed frames, and periodic keyframes.

STEP 03

Persist

Backend links compressed replay chunks to tournament, match, and game IDs.

STEP 04

Render

Widget streams only the required chunks instead of loading a full JSONL file.

P0 · Fix contracts

  • Choose one widget-control transport.
  • Establish one canonical widget catalog.
  • Correct user ID, slug, and port contracts.

P1 · Define replay

  • Create a versioned compact replay DTO.
  • Separate metadata, positions, circles, and events.
  • Keep the existing scoring feed unchanged.

P2 · Stream storage

  • Compress and split recordings into time chunks.
  • Keep metadata in MongoDB and large chunks in file/object storage.
  • Load replay by match ID from the Widget.
